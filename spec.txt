## Problem Statement

The framework is purely request-response. `ApplicationRunner` manages long-lived infrastructure components (`HTTPServer`, `PostgresDB`, `RedisCache`), but there is no seam for async work distribution. A B2B client submitting 1k–100k QR codes for packaging must complete the entire batch within the HTTP server's timeout window, or the request dies. Every bulk job needs a robust queue with concurrency, backpressure, retries, and graceful drain-on-stop logic.

## Solution (Revised)

Rather than reinventing the wheel with a custom `workerpool` and Queue abstraction, we will integrate `hibiken/asynq` (the industry standard for Redis-backed jobs in Go). 

We will build a `workerkit` module that wraps `asynq` into our existing `core.Component` and `core.Lifecycle` seams. This gives us production-grade background jobs with retries, dead-letter queues, and UI monitoring out of the box, while still perfectly honoring `ApplicationRunner`'s graceful startup/shutdown and `healthkit` integration.

## Architecture & Decisions

### Client/Server Separation
To allow scaling HTTP nodes and Worker nodes independently, `workerkit` will expose two separate `core.Component` implementations:
1. `AsynqClient` - Wraps `asynq.Client`. Embedded in HTTP nodes to enqueue tasks.
2. `AsynqServer` - Wraps `asynq.Server`. Embedded in Worker nodes to process tasks.

### Seamless Lifecycle Integration
- Both components embed `core.Lifecycle`.
- `AsynqServer` gracefully starts up the worker pool and correctly handles shutdown (draining in-flight tasks without dropping them on `SIGTERM`).
- Both automatically expose `Liveness` and `Readiness` checks to `healthkit`.

### Functional Options
Configuration uses functional options (e.g. `WithConcurrency`), conforming to the repository standard. An escape hatch (`WithAsynqConfig`) is provided so advanced users can access the underlying `asynq.Config` directly.

### Out of Scope (For Now)
- Embedding the `asynqmon` web UI directly into the framework. This can be run as a separate binary.

## Further Notes
Originated from the architecture review for a B2B QR-generation platform. A mid-flight pivot was made from a custom `workerpool` to `asynq` to strictly follow the "ponytail: lazy senior dev" principle: *Does an already-installed or industry-standard dependency solve it? Use it.*
